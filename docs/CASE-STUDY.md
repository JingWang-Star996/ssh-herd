# 实战案例：四机分布式编码服务（TE-Split）

> Herd 入栏完成后 48 小时内的第一次真实生产实践。本案例已脱敏：
> 4 台机器角色化为 `shepherd`（编码服务机）+ `node-w1/w2/w3`（worker），
> IP 使用文档惯例网段，硬件只描述显存档位。
> 结论先行：**机群搭好只是第一步，框架的价值要在真实负载里长出来。**

---

## 案例背景

需求：一台高显存机器常驻 8.7 GiB 的视觉文本编码器（TE），三台 12–16GB 笔记本
跑 ComfyUI 出图时远程调用它，避免每台都装一份 8GB+ 的编码权重。

最终架构：

```
                 LAN 192.168.1.0/24
  ┌─────────────────────────────────────────────────┐
  │  shepherd (TE 服务, 0.0.0.0:8765)                │
  │    ▲         ▲          ▲                       │
  │    │ HTTP    │          │  （LAN 直连，无隧道）  │
  │  node-w1   node-w2    node-w3                   │
  │  ComfyUI   ComfyUI    ComfyUI（各自隔离实例）     │
  └─────────────────────────────────────────────────┘
```

关键点：**编码服务只此一份**。三台 worker 不各自加载权重——既省显存，
也天然规避了「不同 GPU 浮点舍入经深层网络放大」的跨卡数值不一致问题
（实测同机 HTTP 与原生逐比特一致；跨机长文本误差 0.09，超 0.02 门槛）。

网络路径演进过三轮：**SSH 隧道 → HTTP 网关（AES-GCM）→ LAN 直连**。
直连通了之后按「退役协议」清理：导出旧任务 XML 备份 → 核实 PID 后终止
旧网关/SSH 隧道进程 → 保留恢复材料。每一轮的旧证据都归档不删。

---

## 从这次实战沉淀出的机群运营模式

### 1. 部署隔离优先（血案换来的）

首次在 worker 上起隔离 ComfyUI 实例时，它把该机**用户原有的
`comfyui.db` 移名了**。靠提前留的 `.bak` 按哈希恢复，之后部署脚本
改为「先建隔离数据库再启动」。

**规则：在任何 node 上部署服务前，假设默认路径里住着用户的数据。
隔离目录（用户/输入/输出/临时目录/数据库）先行创建，原物零触碰。**

### 2. 动进程三步核实：identify → verify → act

机群上杀进程/升服务，禁止按进程名模糊匹配：

1. **identify**：先确认 PID 属于本项目（查启动参数、父进程、任务 XML）
2. **verify**：升级前核对旧文件清单哈希 + 队列为空 + 启动参数一致
3. **act**：只对核实过的 PID 动手，其它生产进程（哪怕同机）绝不波及

### 3. 机群滚动升级协议（三台 worker 真实执行过）

```
前置检查（空队列 / 旧版本文件哈希 / 任务与父进程身份）
  → 备份旧文件 + manifest + 计划任务 XML
  → 原子替换（先写临时文件再改名，PS5.1 有空值传递坑，见 PLAYBOOK §11）
  → 升级后冒烟：真实出图一次（禁用回退，确保走的真是新版本）
  → 回执：每台机器留 JSON 证据（新旧哈希、耗时、结果）
```

4 台机器 9 文件升级 3/3 成功、4/4 冒烟出图通过，全程未中断其它服务。

### 4. 版本指纹管理：不匹配就 409，绝不静默回退

权重/代码带 SHA256 指纹，worker 与服务端握手校验：

- 指纹不符 → HTTP 409，**即使开了 fallback 也不回退**（静默回退 =
  用错权重出图，比报错糟糕十倍）
- **服务升级不得覆盖运行配置**——代码和数据/配置分离

### 5. 防火墙规则最小化（跟 Herd 入栏期正好相反）

入栏期要「全开」（Profile=Any）；服务期要「收窄」：

- 规则限定到**具体 exe 路径 + 具体端口 + 指定来源 IP**
- 优先复用系统已有的 Application 放行（如便携 Python 已有规则就不再新增）
- 专用服务用专用端口（8765 编码 / 8766 试验），与 22/8188 互不干扰

### 6. 显存是稀缺资源：互斥 + 守门启动

同一张卡上 TE 服务（9 GiB）与本地推理引擎互斥。启动脚本守门：

- 端口已被监听 → 拒绝启动
- GPU 可用显存低于阈值 → 拒绝启动
- **绝不自动停别的服务**，切回前走显式卸载流程并确认显存释放

### 7. 自启动的取舍：手动计划任务，无开机恢复

重型服务**不设开机自启**——重启后显存被静默占满比「手动起一下」贵得多。
（对照 PLAYBOOK §5：轻量的 sshd 要自启 + 自愈，重型 GPU 服务要手动——
原则是统一的：**每个常驻物都要有明确的生命周期负责人**。）

### 8. 单点观测不下结论

「曾经连不上」不能证明「现在防火墙还拦着」。本次直连前所有超时记录
都是旧观测，现场 `/health` 一试即通。**每次行动前重新测量，旧证据只
归档不引用。**

### 9. 证据链文化

每一次变更留回执：JSON（哈希/耗时/结果）、失败样本不删、
验收口径分开（「可日常用」≠「原任务书全过」）。机群排查时，
上一分钟的回执就是下一分钟的排障入口。

### 10. 跨机并发测试先校时钟

三机并发对比测试前，先用时钟探针校准各机偏差、约定同时开始，
否则毫秒级差异全是钟差噪声。

## 对 Herd 框架的反哺

| 实战发现 | 落到框架的位置 |
|---|---|
| 部署隔离优先 | PLAYBOOK §9 |
| 动进程三步核实 | PLAYBOOK §10 |
| 滚动升级协议 + PS 空值坑 | PLAYBOOK §11 |
| 单点观测不下结论 | PLAYBOOK §12 |
| 入栏期全开 / 服务期收窄 | PLAYBOOK §12（防火墙两阶段） |
| 重型服务生命周期管理 | 本文 §7 |

一句话总结：**入栏解决「机器归你」，实战解决「机器为你干活」——
中间隔着部署隔离、进程核实、升级协议这三道坎，都是撞过才立成规矩的。**
